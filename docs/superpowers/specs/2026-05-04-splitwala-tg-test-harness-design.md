# Splitwala TG Test Harness — Design Spec

**Date:** 2026-05-04  
**Status:** Approved  
**Scope:** End-to-end gramjs userbot harness that exercises all Splitwala Telegram commands in the BCS group and produces a machine-readable JSON report + human-readable markdown summary for Hermes analysis.

---

## 1. Goals

- Verify every Splitwala-TG command surface works correctly from a real user's perspective: correct balances, correct reply text, correct inline-mention rendering.
- Run non-interactively on the Hetzner server (89.167.56.80) alongside Hermes.
- Produce a report readable by both humans and Claude (Hermes) for failure analysis.
- Not coupled to Splitwala internals — pure black-box end-to-end via Telegram.

## 2. Architecture

### Where it lives

```
tg/test-harness/
├── run.js                  # entry point — CLI args, run loop, exit code
├── harness.js              # scenario helper API
├── client.js               # gramjs connection wrapper
├── reporter.js             # builds report.json + report.md
├── login.js                # one-time interactive login to generate session string
├── scenarios/
│   ├── 01-smoke.js
│   ├── 02-split-equal.js
│   ├── 03-split-unequal.js
│   ├── 04-settlement.js
│   ├── 05-history-delete.js
│   ├── 06-reset.js
│   ├── 07-mentions.js
│   └── 08-errors.js
```

Session string and group config live in `.env` (gitignored). No separate `session/` directory needed.

### New npm dependencies

- `telegram` — gramjs (the MTProto userbot client)
- `input` — readline wrapper for the one-time login prompt

### Process model

Single Node.js process. Scenarios run sequentially — one shared Telegram session, one bot, no parallelism. Exits 0 on full pass, 1 on any failure.

### Environment variables

```
TG_API_ID=           # from my.telegram.org
TG_API_HASH=         # from my.telegram.org
TG_USER_SESSION=     # StringSession string, generated once by login.js
TG_TEST_GROUP=       # BCS group chat ID (numeric, e.g. -100123456789)
TEST_SENDER=curls1108
TEST_PARTICIPANT_1=metasmic
TEST_PARTICIPANT_2=vipbhavs
```

`TG_API_ID` / `TG_API_HASH` come from https://my.telegram.org (one-time setup). `TG_USER_SESSION` is generated by running `node tg/test-harness/login.js` once on any machine, then copying the printed string to the server `.env`.

## 3. CLI

```
node tg/test-harness/run.js [options]

Options:
  --scenario <name|all>   run one scenario or all (default: all)
  --report <path>         JSON output path (default: ./report.json)
  --md <path>             markdown summary path (default: ./report.md)
  --timeout <ms>          per-step expectReply timeout (default: 10000)
```

Hermes invocation:

```bash
node /opt/splitwala-webjs/tg/test-harness/run.js \
  --report /var/tmp/splitwala-test-report.json \
  --md /var/tmp/splitwala-test-report.md
```

Exit code 1 signals Hermes that failures occurred; it reads the JSON for analysis.

## 4. Scenario API

Each scenario is an async function `(harness) => void`. The `harness` object exposes:

### Sending

```js
await harness.send(text)
// Sends text to the BCS group as @curls1108. Returns the sent message.

await harness.tapButton(botMessage, labelMatcher)
// Clicks the first inline-keyboard button whose label matches labelMatcher (string or RegExp).
// Waits for the resulting bot reply and returns it.
```

### Receiving & asserting

```js
await harness.expectReply(matcher, opts?)
// Waits up to timeout ms for the next Splitwala-bot message in the group.
// matcher: { contains: string } | { regex: RegExp } | { predicate: (msg) => boolean }
// Throws AssertionError with captured context on timeout or mismatch.
// Returns the gramjs Message object for further inspection.

await harness.expectNoReply(opts?)
// Asserts bot does NOT reply within a short window (default 3s).

harness.assertContains(message, substring)
// Synchronous. Throws if message.text does not contain substring.

harness.assertMentionRendersAs(message, username, expected)
// expected: 'inline' | 'plain-username' | 'text'
// 'inline'        → MessageEntityMentionName entity present (tg://user?id= link)
// 'plain-username'→ MessageEntityMention entity present (plain @username, auto-linked by Telegram)
// 'text'          → no mention entity at all
```

### Lifecycle

```js
await harness.reset()
// Sends /resetall, taps Confirm if an inline keyboard appears, swallows the reply.
// All scenarios start with this.

harness.step(label)
// Sets the current step label for failure reporting. Call before each logical action.

harness.captured()
// Returns array of all bot messages received so far in this scenario.
```

### Error handling

The runner wraps each scenario in try/catch. On failure it records: scenario name, current step label, assertion message, last 5 captured bot messages. It then continues to the next scenario — one failure never kills the run.

## 5. Scenarios

### 01-smoke

Setup: none (no reset needed — just reading)

Steps:
1. Send `/help` → expect reply contains "split" and "balances" (basic help content present)
2. Send `/start` → expect reply contains "SplitWala" and "group" (correct group-mode response)

### 02-split-equal

Setup: `harness.reset()`

Note: `/split` routes through the LLM wizard. The wizard may ask clarifying inline-keyboard questions before showing the final Confirm button. The harness taps through any intermediate prompts (accepting defaults) until Confirm appears.

Steps:
1. Send `/split 600 @metasmic @vipbhavs @curls1108`
2. Expect reply contains "Confirm" → tap Confirm button
3. Expect reply contains "600" (success confirmation)
4. Send `/balances`
5. Expect reply contains "200" and references all three participants
6. Assert @curls1108 mention renders as `'inline'` (ID known — sender has history in group)
7. Assert @metasmic and @vipbhavs render as `'plain-username'` (IDs unknown until they message)

### 03-split-unequal

Setup: `harness.reset()`

Note: `/split` routes through the LLM-powered wizard (`tg/split-wizard.js`), so the harness sends natural language and the wizard may ask clarifying questions via inline keyboard before reaching confirm. The harness must handle intermediate wizard prompts (tap any clarifying buttons) before seeing the final Confirm button.

Steps:
1. Send `/split 600 @metasmic owes 400 and @vipbhavs owes 200` (natural language unequal split)
2. Handle any intermediate wizard prompts (tap inline buttons as needed until Confirm appears)
3. Tap Confirm
4. Expect success reply
5. Send `/balances`
6. Expect reply contains "400" for @metasmic and "200" for @vipbhavs

### 04-settlement

Setup: `harness.reset()`

Steps:
1. Send `/split 600 @metasmic @vipbhavs @curls1108` → confirm
2. Send `/paid 200 to @metasmic` (record that @metasmic paid curls1108 back 200)
3. Expect success reply
4. Send `/balances` → expect net balance for @metasmic is now 0
5. Send `/got 100 from @vipbhavs`
6. Expect success reply
7. Send `/balances` → expect @vipbhavs balance reduced by 100

### 05-history-delete

Setup: `harness.reset()`

Note: `/history` output format is `1. [date] payer paid amount` — no transaction IDs are shown. `/delete` with no args shows an inline keyboard of recent transactions (buttons like "1. X paid ₹300"). The harness taps the first button on that keyboard to delete the most recent transaction.

Steps:
1. Send `/split 300 @metasmic @curls1108` → confirm
2. Send `/history` → expect reply lists the split (contains "paid" and "300")
3. Send `/delete` (no args) → expect an inline keyboard listing recent transactions
4. Tap the first transaction button (most recent split)
5. Expect a confirmation prompt (Confirm / Cancel) → tap Confirm
6. Send `/history` → expect reply shows "No matching transactions" or empty (or no longer contains the deleted entry)

### 06-reset

Setup: none

Steps:
1. Send `/split 500 @metasmic @curls1108` → confirm
2. Send `/resetall` → tap Confirm
3. Send `/balances` → expect reply is the "no balances" / empty-ledger message

### 07-mentions

Setup: `harness.reset()`

Steps:
1. Send `/split 600 @metasmic @vipbhavs @curls1108` → confirm
2. Capture the bot's confirmation reply
3. `assertMentionRendersAs(reply, 'curls1108', 'inline')` — ID known
4. `assertMentionRendersAs(reply, 'metasmic', 'plain-username')` — ID unknown
5. `assertMentionRendersAs(reply, 'vipbhavs', 'plain-username')` — ID unknown
6. Send `/balances` → repeat the same entity assertions on the balance reply

### 08-errors

Setup: `harness.reset()` (clean ledger to provoke meaningful errors)

Steps:
1. Send `/split` (no args) → expect reply is a friendly error (not a stack trace; contains "usage" or participant count hint)
2. Send `/paid 100 to @nobodyhere` → expect friendly error (unknown participant)
3. Send `/delete nonexistent-id` → expect friendly error

## 7. Hermes integration

Hermes (systemd service `hermes-gateway`) invokes the harness as a shell command and reads the JSON output. The integration has three phases:

**Phase 1 — manual:** Run `node tg/test-harness/run.js` from your terminal. Read `report.md` yourself. Paste failures to Claude for analysis.

**Phase 2 — Hermes-invoked:** You tell Hermes "run the Splitwala tests." Hermes shells out, reads `report.json` when done, and you ask Claude: "analyse the test results at `/var/tmp/splitwala-test-report.json`." Claude reads the JSON and gives you a diagnosis.

**Phase 3 — automated:** Hermes runs the suite on a schedule (e.g. after each deploy, or nightly) and proactively notifies you of failures.

The harness has no dependency on Hermes — it is a standalone CLI tool that Hermes happens to call.

## 8. Validation strategy

1. **Local dev (Windows):** Run `node tg/test-harness/login.js` once to generate `TG_USER_SESSION`. Then run `--scenario smoke` only. Get that green.
2. **Expand locally:** Run `--scenario all`. Fix any assertion mismatches against real bot replies.
3. **Deploy to server:** Copy session string to server `.env`. Run from server shell as `node`. Confirm all 8 pass.
4. **Wire Hermes:** Teach Hermes the shell command. Confirm it can invoke and read the report.

## 9. Out of scope (v2)

- DM-mode `/start` testing (requires userbot to message bot 1-on-1)
- Parallel scenario execution
- Automatic re-run on failure with exponential backoff
- WhatsApp harness
- Hermes autonomously fixing failures (requires Claude API integration beyond current Hermes setup)
